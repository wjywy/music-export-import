# 真·写入：网易云 / QQ 音乐 / 酷狗 可行性方案

> 目标：让用户在渡口点一下，歌单就出现在自己的网易云 / QQ 音乐 / 酷狗账号里。
> 本文回答三件事：能不能做、做到什么程度、用哪条路做才不会把项目做死。

## 0. 结论

| 平台 | 有官方写入 API 吗 | 私有接口能写吗 | 推荐路径 |
| --- | --- | --- | --- |
| 网易云音乐 | 没有（对个人开发者） | 能：新建歌单、收藏单曲到歌单 | 文本桥 / 官方导入（默认）+ 本机扩展（实验） |
| QQ 音乐 | 没有（对个人开发者） | 能：`musicu.fcg` 的 `PlaylistBaseWrite` / `PlaylistDetailWrite` | 文本桥 / 官方导入（默认）+ 本机扩展（实验） |
| 酷狗音乐 | 没有（对个人开发者） | 能：新建歌单、对歌单添加歌曲 | 文本桥 / 官方导入（默认）+ 本机扩展（实验） |

一句话：**三家都「技术上能写」，但都「没有给个人开发者的官方写入授权」**。所以「授权 App 登录」拿到的是用户的登录态，不是平台的写入许可；能写，靠的是拿用户登录态去调平台的私有接口。这决定了方案的重心不是「怎么调通」，而是「怎么把风险关在用户自己的浏览器里」。

直接回答你的问题：

- 如果「授权」指**把账号 Cookie / Token 交给渡口服务端**：能跑通，但不建议做成产品（见 3.A）。
- 如果「授权」指**用户在自己浏览器里登录、由本机扩展代操作**：行得通，这是本方案的 L1。
- 如果不想装任何东西：走**文本桥 + 三家 App 自带的官方导入**，这是 L0，今天就能上。

补充：你给的 GoMusic 走的是第三条路——文本桥，不是账号写入；它验证了 L0，也暴露了 1000 字符 / 手动合并的痛点（见 2.4）。

范围说明：酷我不在本轮，写入能力未实测；Apple Music 已经用 MusicKit 实现了真实写入（见 2.5），它的官方授权路径是这三家没有的。

## 1. 先把「授权登录」说清楚

「授权登录」在音乐平台这里有三层，能力完全不同：

| 形态 | 拿到什么 | 能做什么 | 能不能写歌单 |
| --- | --- | --- | --- |
| 官方 OAuth / 开放平台授权，且带写入 scope（如 Apple Music MusicKit） | 用户授权令牌，scope 明确 | 读写用户资料库 | 能。令牌可撤销，加密后可存 |
| 官方 OAuth / 开放平台授权，但没有写入 scope（网易云 / QQ / 酷狗） | `openid`、昵称、头像，或播放授权 | 登录、展示身份、按协议播放 | 不能。没有 `playlist.write` 这个 scope |
| 用户把账号 Cookie / 会话交给服务端 | 完整的账号会话 | 读取、搜索、增删歌单，几乎所有网页操作 | 能，但等于把账号控制权交给了服务器 |
| 用户在本机浏览器里已登录 | 浏览器里的会话，不出本机 | 由本机扩展代用户操作 | 能，且凭证不离开用户设备 |

关键差别：**第一种是平台给的、有边界的写权限；后两种是借来的账号控制权，其中本机登录态把控制权留在用户手里**。前者可以合规地做成产品（Apple Music 已经这么做），而把账号会话存到服务端，一旦出事，是平台风控 + 用户账号 + 我们的数据库三输。

默认方案不碰账号会话；但「扫码后全自动写入」必须用到会话，所以扫码写入作为用户的显式选择单独处理：

- 只存 AES-256-GCM 加密后的会话，不存密码；
- 不写日志、不落明文，可随时断开；
- 会话只用于新建歌单，不改动已有歌单；
- 使用平台非公开接口，风控 / 改版风险要在 UI 里写明。

Apple Music 的 OAuth 令牌是 scope 明确的官方授权，和借来的账号会话不是一回事；但两者都应该加密存储、可撤销。

## 2. 事实核查

### 2.1 官方通道：今天就能用，而且三家都有

三家 App 都内置了「导入外部歌单」，这是平台自己提供的迁移能力，不需要我们碰凭证。

| 目标平台 | 官方入口 | 输入形式 | 已知限制 | 来源 |
| --- | --- | --- | --- | --- |
| QQ 音乐 | App：我的 → 更多 → 导入外部歌单；网页「导入外部歌单」页 | App 三种：链接 / 文字、图片、账号（仅其他 QQ 账号）；网页：文字 | 网页版官方建议 ≤ 500 首；文字导入约 1000 字符/次（用户反馈）；曲库差异会漏歌 | [QQ 音乐导入页](https://y.qq.com/y/static/mymusic/songlist_import.html)、[天极网教程](https://mydown.yesky.com/news/195233.html) |
| 网易云音乐 | 我的 → 导入外部歌单 | 粘贴歌单链接 | 公开教程以 QQ 音乐链接为例；其他来源需实测 | [百度经验教程](https://jingyan.baidu.com/album/19192ad891ff8aa43e5707dd.html) |
| 酷狗音乐 | 首页 → 自建歌单 → ＋ → 导入歌单 | 粘贴歌单链接，选「匹配歌单」 | 支持 QQ 音乐、网易云、咪咕、酷我、虾米等来源 | [天极网教程](https://mydown.yesky.com/news/282602.html) |

这条路的价值：**零凭证、零封号风险、平台自己负责匹配**。缺点是用户要离开渡口，跳进目标 App 操作 3–4 步；而且它对来源有要求：QQ 可以吃链接 / 文字 / 图片，网易云与酷狗以链接为主，渡口自建歌单只有 QQ 的文本桥能覆盖。

### 2.2 私有接口：技术上确实能写

以下都是维护中的开源实现，说明接口形态存在；它们也都明确写着「非官方、可能随上游改版失效」。

| 平台 | 写能力 | 关键凭证 | 已知风险 | 来源 |
| --- | --- | --- | --- | --- |
| 网易云 | `POST /api/playlist/create` 新建；`/api/playlist/manipulate/tracks?op=add` 加歌；另有改歌单名/描述/封面、删歌单、调歌曲顺序 | `MUSIC_U` + `__csrf`（`csrf_token`） | 境外或云服务器 IP、高频请求可能触发 `460 cheating` 异常；接口随时改 | [NeteaseCloudMusicApi 文档](https://cdn.jsdelivr.net/gh/sssnan/NeteaseCloudMusicApi@684c581fe002e46a0164d5a0b1e5cc2da7a118f2/docs/README.md) |
| QQ 音乐 | `musicu.fcg` 的 `PlaylistBaseWrite` / `PlaylistDetailWrite`：建歌单、批量加歌/移歌、删歌单 | `uin` + `qqmusic_key`，请求体 `comm` 字段与签名 | 每批最多 20 首；设备数有上限，新设备可能触发 `20279`；改版即失效 | [qqmusic-mcp](https://github.com/baoozak/qqmusic-mcp)、[qq-music-api](https://github.com/yakult-green-tea/qq-music-api) |
| 酷狗 | 新建歌单、对歌单添加歌曲、删歌单 | `token` + `userid` + `dfid`，部分请求要签名 | 概念版与普通版 token 不通用；签名/设备指纹随版本变 | [KuGouMusicApi](https://github.com/MakcRe/KuGouMusicApi) |

### 2.3 官方开放平台：有入口，但没有我们要的能力

- 酷狗有开放平台（<https://open.kugou.com>），腾讯音乐、网易云也有面向音乐人、硬件、内容合作的开放体系。
- 公开资料里**没有找到面向个人开发者的「创建歌单 / 写入用户歌单」API**；这类能力通常只对商务合作方开放，需要企业主体、合同与审核。
- 结论：个人项目 / 小团队现在拿不到官方写入授权，不要把它写进路线图的第一阶段。

### 2.4 GoMusic 的实测对照：文本桥，不是账号写入

你给的 [music.unmeta.cn](https://music.unmeta.cn/)（开源项目 [GoMusic](https://github.com/Bistutu/GoMusic)）确实让「网易云 / QQ 音乐互转」变得可用，但实现方式值得看清楚：

1. 输入网易云 / QQ / 汽水歌单链接；
2. 站点后端把歌单转成纯文本，默认「歌名 - 歌手」，可选「歌手 - 歌名」「仅歌名」，支持正序 / 倒序；
3. 复制文本，粘贴到 TuneMyMusic / Spotlistr，或目标 App 的官方导入入口。

它**不登录用户账号，也不调用任何写接口**。README 里「如何迁移至网易云 / QQ 音乐」只有一行：见 [issue #17](https://github.com/Bistutu/GoMusic/issues/17)。

issue #17（已关闭）里能确认三件事：

- 维护者回复「默认支持，只是 QQ 音乐对每次导入的音乐数量有限制」，配图是 QQ 音乐 App 的「新建 | 导入」页（文字导入 / 图片导入 / 账号导入，账号导入仅支持其他 QQ 账号）；
- 用户反馈 QQ 单次约 1000 字符，大歌单要分多次导入、再手动合并；
- 另有用户反馈 183 首只导出 30 首（解析分页问题，在 GoMusic 侧，不在导入侧）。

所以它证明的是「**文本桥 + 平台官方导入**」可行，不是「授权登录后直接写账号」可行。两个方向用的还是两套官方入口：网易云 → QQ 走 QQ 的链接 / 文字导入（GoMusic 的场景是文字）；QQ → 网易云走网易云的「导入外部歌单」（粘贴 QQ 链接）。

这正好把 L0 坐实了，也把 L0 的痛点暴露出来：1000 字符、分页截断、手动合并。我们的 L0 要比它多做三件事：格式可选、按目标限制自动分段、分页完整并给出合并步骤。

### 2.5 反例：Apple Music 已经能真写

仓库现在有一条真实的写入路径：用户在设置页完成 MusicKit 授权后，后端用开发者 JWT + `music-user-token` 调 `POST /v1/me/library/playlists` 建资料库歌单，再 `POST /v1/me/library/playlists/:id/tracks` 加歌（`apps/api/src/apple/apple-music.service.ts`）。这证明「官方授权 → 写入」是成立的，不需要猜接口。

它不能复制到网易云 / QQ / 酷狗，原因不是技术，而是授权模型：Apple 把「写用户资料库」作为 MusicKit 的正式能力开放；三家国内平台没有给个人开发者对应的 scope。所以对这三家，要么走文本桥，要么借用户本机登录态。

也正因为 Apple 这条路径是官方且可撤销的，它的令牌可以加密入库；三家账号 Cookie 不应该照搬这个做法。

### 2.6 同类产品：小熊歌单搬家

一个已经上架的 Chrome 扩展「[小熊歌单搬家](https://playlist.victor42.work/)」做了几乎同样的事：把 QQ / 网易云歌单导出，导入到酷狗、汽水、网易云、QQ；电脑端提取，扫码衔接到手机；免费。介绍见 [APP喵](https://www.appmiao.com/article/415)。

它的存在说明两件事：

- 「扩展 + 手机接力」这条路有真实产品，不是纸上推演；
- 但它的实现没有公开，无法判断用的是官方导入还是私有接口，所以只能当可行性佐证，不能当授权依据。

它的「电脑提取 + 扫码到手机」值得借鉴：手机端不装扩展，扫码打开一个只读迁移页，复制已经分好段的文本，再跳目标 App 导入。这能补上 L1 只覆盖桌面浏览器的问题。

## 3. 三条路线对比

| | A. 服务端代登录 | B. 浏览器扩展（本机写入） | C. 文本桥 + 官方导入 |
| --- | --- | --- | --- |
| 用户体验 | 最好：授权后一键完成 | 较好：装一次扩展，之后一键 | 一般：复制 → 打开 App → 粘贴；大歌单还要分段合并 |
| 技术可行性 | Demo 能跑通 | 高，三家都能覆盖 | 确定可行，GoMusic 已验证 |
| 凭证安全 | 差：Cookie = 账号控制权 | 好：凭证不出本机 | 最好：不接触凭证 |
| 合规 / 封号风险 | 高：服务器 IP 批量写，最像爬虫 | 中：仍是私有接口，但由用户本机、用户触发 | 低：平台官方能力 |
| 维护成本 | 高：登录、风控、签名都在服务端 | 中：每平台一个适配器 | 低：文案、分段与跳转 |
| 结论 | **不做** | **做，但只做实验版** | **默认路径，先上** |

## 4. 推荐方案：双层交付

### 4.1 L0：文本桥 + 官方导入（默认，先上）

这一层不是「跳转一下」，而是把 GoMusic 已经验证过的文本桥做成一张可交付的迁移卡片。目标平台不同，入口和输入形式不同：

| 目标 | 官方入口 | 输入 | 能覆盖的来源 | 已知限制 |
| --- | --- | --- | --- | --- |
| QQ 音乐 | App：我的 → 更多 → 导入外部歌单 | 链接 / 文字 / 图片 / 账号（仅其他 QQ 账号） | 任意来源（文字 / 图片）；平台链接（链接） | 文字约 1000 字符/次（用户反馈，需实测）；链接支持哪些源平台需实测 |
| 网易云 | 我的 → 导入外部歌单 | 链接 | 仅平台分享链接（至少 QQ 音乐） | 渡口自建 / 合并歌单没有可粘贴的链接 |
| 酷狗 | 自建歌单 → ＋ → 导入歌单 | 链接 | QQ / 网易云 / 咪咕 / 酷我 | 同上 |

覆盖矩阵：

| 来源 | → QQ 音乐 | → 网易云 | → 酷狗 |
| --- | --- | --- | --- |
| 平台公开链接 | 链接 / 文本均可（链接支持范围需实测） | 链接导入 | 链接导入 |
| 渡口自建、合并、手动歌单 | 文本桥 | 不支持，需 L1 或手工 | 不支持，需 L1 或手工 |
| Apple Music 等无公开链接来源 | 文本桥 | 不支持 | 不支持 |

迁移卡片的内容：

1. 目标平台与对应入口（App 深链 / 网页 / 二维码）；
2. 默认 `歌名 - 歌手` 的文本，按目标限制切成若干段（QQ 先按 900 字符，留余量），每段一个「复制第 N 段」按钮；
3. 段数、曲目数、预计需要导入几次；
4. 分段导入后的合并步骤（QQ 目前需要手动合并，不假装能自动）；
5. 「我已完成」自报转化，不假装服务端能验证。

现有 `txt` 导出是 `歌手 - 曲名`，与 QQ 文字导入的常见格式相反；L0 应新增 `text` 格式（可带 `format` / `order` / `chunk` 参数），不要改旧格式，避免破坏已有下载。

这一层约 3–4 天，完全不碰凭证，能兜住「用户不想装扩展」「扩展被商店下架」。

### 4.2 L1：本机写入扩展（实验，先做网易云）

> 实施偏差：最终按用户要求做成了**服务端扫码会话**（见第 10 节），不是浏览器扩展；本节保留扩展方案，作为不把会话放到服务端的备选。

架构：

```
┌─────────────┐   任务 JSON（含一次性 token）   ┌──────────────────┐
│  渡口 Web    │ ─────────────────────────────▶ │  浏览器扩展       │
│  (我们的站)  │ ◀───────────────────────────── │  (用户本机)       │
└─────────────┘        执行结果 / 回读结果       └────────┬─────────┘
       │                                                  │ 在目标站点页面上下文里 fetch
       │ 只存任务、匹配结果、状态                          ▼
┌─────────────┐                                  ┌──────────────────┐
│  渡口 API    │                                  │ music.163.com    │
│  不存 Cookie │                                  │ y.qq.com         │
└─────────────┘                                  │ kugou.com        │
                                                 └──────────────────┘
```

为什么不是服务端直接写：

- Cookie 不落库，泄露面从「整个账号」降到「一次任务」；
- 请求从用户自己的浏览器、自己的 IP、自己的设备指纹发出，风控画像正常；
- 用户能看见扩展在做什么，随时可停；
- 出问题只需下架扩展，不用处理用户凭证泄露。

「登录」这一步也不经过我们：扩展检测到未登录时，打开平台官方登录页，用户自己扫码或输密码，会话留在浏览器里。我们不实现二维码协议，不接管登录表单，也不接触密码。

覆盖范围要说清楚：L1 的自动写入只覆盖**桌面 Chrome / Edge**；手机用户不装扩展，走「扫码接力」——桌面端生成二维码，手机扫码打开渡口的只读迁移页，复制已分段的文本 / 链接，再跳目标 App 官方导入。这样移动端仍能用到渡口的匹配与分段，只是最后一步仍是官方入口，而不是 L1 的自动写入。

验证期可以先用一个油猴脚本（只跑在目标站点）代替扩展，验证接口与失败模式；确认能稳定跑通后，再把同一套逻辑搬进 MV3 扩展。这样 P1 的第一周不需要处理商店审核。

#### 任务协议（服务端 → 扩展）

```json
{
  "jobId": "wj_01J...",
  "platform": "netease",
  "mode": "create",
  "playlist": {
    "name": "深夜渡口",
    "description": "由渡口从 QQ 音乐迁移",
    "visibility": "private"
  },
  "tracks": [
    {
      "sourcePlatform": "qq",
      "sourceId": "0039MnYb0qxYhV",
      "title": "晴天",
      "artist": "周杰伦",
      "targetId": "186016",
      "targetTitle": "晴天",
      "targetArtist": "周杰伦"
    }
  ],
  "limits": { "batchSize": 20, "requestIntervalMs": 800 },
  "expiresAt": "2026-10-22T17:00:00+08:00"
}
```

服务端只下发「已匹配好的目标歌曲 id」，扩展不做搜索、不做打分，避免把匹配逻辑散到两端。

#### 执行流程（每个平台一致）

1. **能力探针**：建一个临时歌单 → 加 1 首 → 回读 → 删掉。任何一步失败，本次任务直接判 `unsupported`，不写用户数据。
2. **确认**：扩展读出当前登录账号昵称，展示「将向 XXX 的账号写入 N 首」，用户点确认。
3. **建歌单**：同名歌单已存在时停止并让用户选择「追加到它」或「改名新建」，不自动覆盖。
4. **分批加歌**：QQ 每批 ≤ 20，网易云/酷狗按实测 50–100；每批之间 0.8–1.2 秒抖动；每批写后回读校验。
5. **报告**：逐首返回 `added` / `duplicate` / `unavailable` / `failed`，附目标歌单链接。
6. **回滚**：只允许删除「本任务创建的这张歌单」，绝不碰用户已有歌单，绝不碰「我喜欢」。

#### 三平台适配要点

| | 网易云 | QQ 音乐 | 酷狗 |
| --- | --- | --- | --- |
| 在哪个页面执行 | `music.163.com` | `y.qq.com` | `kugou.com` |
| 登录态 | `MUSIC_U`、`__csrf` | `uin`、`qqmusic_key` | `token`、`userid`、`dfid` |
| 写接口 | `/api/playlist/create`、`/api/playlist/manipulate/tracks` | `musicu.fcg` 的 `PlaylistBaseWrite` / `PlaylistDetailWrite` | 新建歌单 / 歌单加歌接口 + 签名 |
| 批量 | 实测后定（建议 50–100） | 20 / 批 | 实测后定 |
| 典型失败 | `460` 风控、登录过期 | `20279` 设备上限、签名变化 | token 版本不匹配、签名变化 |
| 建议顺序 | **第一个做**（Web 接口最直接） | 第二个 | 第三个（签名最麻烦） |

#### 幂等、回滚、风控

- 任务带 `idempotencyKey`（用户 + 歌单 + 目标平台 + 内容哈希）；重复点击返回同一任务，不重复建歌单。
- 歌单名默认加日期后缀（`深夜渡口 · 2026-10-22`），降低同名冲突。
- 写前探针 + 写后回读；探针不过，整个平台写入开关自动关闭（服务端记录 `capabilities`）。
- 遇到 460 / 20279 / 登录跳转，立即停止，不重试、不换代理、不绕验证码。
- 限速：每用户 10 分钟内 1 个任务；单任务 ≤ 1000 首；不做定时批量、不做无人值守。
- 扩展只允许渡口域名通过 `externally_connectable` 投递任务；任务 token 一次性、10 分钟过期、绑定 `jobId`。

#### 安全边界

- 不收集账号密码；不读、不上传 Cookie；不在服务端日志里打印任何 `Set-Cookie`。
- 扩展不加载远程代码（MV3 要求）；所有平台适配逻辑随扩展版本发布。
- 服务端只存：任务、目标歌曲 id、逐首结果、目标歌单 id / 链接。
- 用户可一键断开：扩展侧删除本地任务缓存，服务端把任务标记为 `revoked`。

### 4.3 明确不做

- 不做「输入手机号 + 密码 / 验证码」的代登录；
- 不把明文 Cookie / Token 存进 MySQL 或对象存储；扫码写入的会话必须加密存储、可随时断开；
- 不做「导入到我喜欢」——「我喜欢」是用户私有数据，误写/误删代价太高；
- 不做后台定时同步、批量多账号、代理池；
- 不把「私有接口写入」包装成「官方支持」。

| 场景 | 预期 |
| --- | --- |
| 183 首 / 超过 1000 字符 | 完整解析，自动切成 ≤ 900 字符的段，不截断歌曲行，给出合并步骤 |

## 8. 风险与 Go/No-Go

| 风险 | 说明 | 缓解 |
| --- | --- | --- |
| 封号 / 限流 | 私有接口不是平台许可，高频或异常设备会触发风控 | 用户本机、用户触发、限速、探针、熔断、单任务上限 |
| 接口改版 | 签名、字段、域名随时变 | 每平台独立适配器；探针不过自动关开关；不承诺 SLA |
| 隐私合规 | 若存 Cookie，属于账号凭证，泄露责任大 | 本方案不存凭证；只存任务与结果 |
| 扩展商店审核 | 远程代码、权限过宽会被拒 | MV3、最小权限、无远程代码、隐私政策 |
| 用户预期 | 用户会以为「官方支持」 | 文案明确「实验性，可能失败，可回滚」 |
| 维护成本 | 三平台持续跟进 | 先做网易云；QQ/酷狗按用量决定；不做的平台回落到 L0 |

**Go/No-Go 判据**：P1 上线后两周，若网易云探针成功率 ≥ 95%、任务完成率 ≥ 80%，再做 QQ / 酷狗；若连续出现风控或改版导致探针失败，停止 L1，把 L0 做深（更顺的官方导入引导）。

## 9. 需要拍板的三件事

1. 是否接受「装扩展」这个门槛？接受 → 做 L1；不接受 → 只做 L0。
2. 是否同意「先只做网易云」？三平台同时做，维护成本会翻三倍。
3. 是否能接受「实验性 + 可能封号」的风险提示？不能 → L1 不上线，只保留官方导入。

## 10. 实施记录（2026-10-22）

**文本桥（P0）**

- `GET /playlists/:id/transfer?target=qq|netease&format=&chunk=`，核心逻辑在 `apps/api/src/playlists/transfer.ts`；
- 歌单详情页「迁移」对话框：QQ 文本分段、网易云链接、复制 / 下载、分段与合并步骤；
- 真实验证：QQ 66 首歌单 → 网易云原始链接；网易云 198 首歌单 → QQ 4 段、最大 899 字符、198 行无截断。

**扫码写入（L1，改用服务端会话）**

- 最终没有做浏览器扩展，而是做了服务端扫码：用户在迁移面板扫一次码，渡口用加密保存的会话直接建歌单；
- 网易云：`NeteaseCloudMusicApi` 的 QR key / create / check + `playlist_create` / `playlist_tracks`；
- QQ 音乐：`@yakult-green-tea/qq-music-api` 的 serverless handler，手机 QQ 扫码，`/user/playlist/create` + `/user/playlist/tracks`，mid 通过 `/song/batch` 换成数字 id；
- 会话存 `platform_credentials`，AES-256-GCM 加密，可断开；不做密码代登录；
- 已实测：两端二维码生成、扫码 801/802/803、登录态入库；真实写入网易云隐私歌单 2 首（晴天 / 富士山下）、QQ 音乐歌单 2 首，均回读确认；测试产生的重复歌单已清理；
- 踩坑记录：网易云 `playlist_track_add` 返回 401 无权限，改用 `playlist_tracks` + `crypto: 'weapi'` 并解包 `body.body`；QQ `/song/batch` 的 `results` 在顶层，创建歌单返回扁平 `{ tid, dirId, name }`，且会追加 `_时间戳` 后缀。

**测试**：单元 20 项、Nest e2e 18 项、Playwright 7 项通过。
